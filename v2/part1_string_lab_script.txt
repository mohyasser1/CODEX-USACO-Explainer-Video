PART 1 GUIDED LAB — FIND THE FIRST ONE THAT APPEARS ONCE
Status: substantive extension for the requested faster delivery. Program first_unique.cpp.

[Rohail labels rehearsal requests with uppercase letters. Example SWISS, indices0..4.
Question: first position whose letter occurs exactly once in the whole string.]
Rohail is testing a tiny rehearsal-request system before connecting it to any real names. Each request has one uppercase letter as a label. Maya asks for the first request whose label appears exactly once in the entire list. Their test string is SWISS. This is a deliberately small model: the letters are labels, not initials that uniquely identify actual students. The program must print a zero-based position, or negative one if no position qualifies. Notice the two requirements hiding in the sentence. A label must be globally unique, and among those labels we need the earliest position in the original order.

[Wrong proposal: return the first letter seen. S initially unseen, but later repeats.]
Rohail suggests keeping a set and returning the first letter that is new. That would immediately return position zero, because the first S has not appeared before. Maya covers the rest of the string, then uncovers it. There are two more S labels waiting later. New so far is not the same as occurs once in the complete input. The mistake is about information, not C plus plus syntax. Before selecting an answer, they must know how often each label appears across the entire list. A decision made too early cannot see the future requests that invalidate it.

[Define frequency[0..25], all zero. A maps0, B maps1, ..., Z maps25.]
Because the alphabet contains exactly twenty-six uppercase English letters, an array of twenty-six counters is enough. Counter zero belongs to A, counter one to B, and so on. On the contest platform, subtracting the character A from an uppercase letter produces its offset in this alphabet. The input contract matters here: lowercase letters, spaces and arbitrary text are not silently valid indices. Our learning program checks every character before using the offset. If the application needed real names or a larger alphabet, a different representation would be appropriate. A convenient twenty-six-box picture does not make every string problem an uppercase-letter problem.

[Two representations: s stores order; frequency stores multiplicity. Neither replaces the other.]
Sam asks whether the count array means they can throw the original string away. Rohail points back to the word first. The frequency table remembers how many times a label occurs, but not where its occurrences were. For our final ordered scan, we keep the string too. These are two summaries with different jobs: the string preserves positions, and the counter array answers how often. Memory is not just a pile of interchangeable boxes. Choosing which information to retain follows directly from the questions the algorithm must answer. If we discard order and later need it, clever loops cannot reconstruct information we never saved.

[Scan SWISS: S1; W1; I1; S2; S3. Final nonzero counts I1,S3,W1.]
Initialize every counter to zero. Read the first S and increase its counter to one. Read W and increase W to one. Read I and increase I to one. The next S changes the existing S counter from one to two; it does not create a second counter. The final S increases that same counter to three. At the end, S has count three, W has count one, and I has count one. Every other uppercase letter has count zero. A label with count zero did not occur, so it cannot provide a position in the input. That observation will matter when we choose where to scan next.

[Wrong answer order: scanning alphabet returns I before W. Original positions: W1,I2.]
Maya asks for the answer, and Rohail starts scanning the counters alphabetically. He reaches I before W and almost reports it. Sam points to the request order: W was at position one, while I was at position two. Both occur once, but W is earlier. Scanning the alphabet solves a different problem, the alphabetically smallest unique label. Our problem asks for the earliest unique position. So the second pass must follow the original string from left to right. This is a useful kind of counterexample because the frequencies are completely correct; only the order used to select the answer is wrong.

[Second scan: i0 S has3 ->skip; i1 W has1 ->return1.]
At position zero, the letter is S. Its final count is three, so skip it. At position one, the letter is W. Its final count is one, so return one immediately. We do not need to inspect I to prove that W is earlier. Every earlier position has already failed the count-equals-one test. The returned number is an index, not the character code for W and not the count one merely because that count happened to match. In this example the output is the integer one for position one. Keeping the units attached to variables prevents this accidental numerical coincidence from hiding a misunderstanding.

[Invariant for counting: after k characters, each counter equals occurrences in s[0:k].]
The first pass has a familiar invariant. After processing the first k characters, each counter equals the number of occurrences of its letter among those k characters. Initially all counters are zero because no characters have been processed. Processing the next character increases exactly its counter, leaving every other letter's count unchanged. That preserves the statement for the longer prefix. When the scan finishes, the processed prefix is the whole string, so the counts are global. This proof explains why the final frequencies can be trusted by the second pass; it does not yet prove which position we should return.

[Second-pass invariant: every earlier position failed. First qualifying position is earliest.]
For the second pass, use a different invariant: before testing position i, every earlier position has a letter whose final count is not one. If the current count is one, the current position qualifies and no earlier position does, proving it is the requested earliest answer. If the count is not one, skipping it preserves the invariant for the next index. If the loop finishes without returning, every position has failed, so negative one is correct. Rohail writes two short proofs beside two short loops. Combining loops into one sentence would have hidden the fact that they establish different things.

[Code: getline; array<int,26> frequency{}; two scans; return0 on success.]
Now read the implementation. Getline reads the complete input line, so an empty line is a legitimate empty string in our teaching contract. The braces after the array declaration initialize all twenty-six counters to zero. Forgetting initialization would make increments depend on values that do not represent our empty-prefix state. The first loop validates and counts characters. The second loop uses an integer position to access the string, consults the matching frequency, prints the first qualifying index, and exits. If there is no early return, the final statement prints negative one. That final output is outside the loop, so it happens once, not once per failed character.

[Bounds n<=100000. Counters<=n. Two n scans plus26 zero initializations.]
With at most one hundred thousand characters, each counter fits in int. The string uses linear storage. The frequency table always contains twenty-six counters, so its extra storage is constant relative to input length. Two complete scans take two times n steps, plus constant initialization, giving linear time. A simpler slow solution could count the current character by scanning the entire string at every position. That takes quadratic time in the worst case. It is a useful small-input oracle, but Rohail would not want a hundred thousand repeated requests to turn one dashboard lookup into billions of comparisons.

[Testing variants: empty line, A, AAAA, SWISS, BANANA, ZYX. No answer on question scene.]
Maya now changes the input instead of letting Rohail admire SWISS forever. I always find something wrong: she borrows that supplied Runaway hook for her testing mission. She is looking for a specific counterexample, not declaring that every program must be broken. Predict the outputs for an empty line, a single A, four copies of A, BANANA, and ZYX. Then explain which test would catch the alphabetic-scan mistake and which would catch returning the first unseen letter too soon. Pause the video and write the positions, not just the qualifying letters. A good test set is a collection of challenges to specific assumptions. Five random words may exercise the same easy path, while one carefully chosen word can expose the exact mistake you made.

[Answer:empty-1;A0;AAAA-1;BANANA0;ZYX0. Alphabetic wrong picks X at2.]
The empty input has no position, so its answer is negative one. A single A returns zero. Four copies of A return negative one. BANANA returns zero because B occurs once at the first position. ZYX also returns zero: Z is first, even though X comes earlier alphabetically. That last case exposes the alphabetic-scan mistake. SWISS and the all-A case expose the temptation to return a label merely because it is new when first encountered. Our independent oracle directly counts each candidate letter across the whole input, then selects the first successful position. It is slower but uses the simplest meaning of the problem.

[Change request: first repeated label versus first globally unique position. Contract written above code.]
Finally, Sam asks for the first label whose second occurrence arrives. That is a different request. A left-to-right scan can answer it as soon as a counter reaches two, because future characters cannot undo the fact that a repeat has occurred. Rohail does not automatically reuse the two-pass answer rule. He compares what information each question requires and when that information becomes available. The lesson is larger than frequency arrays: before optimizing, decide whether your answer depends on the complete future input or on something already settled by the prefix you have seen. That decision often determines the shape of the algorithm.
