PART 2 INTRODUCTION — A GREEDY CHOICE NEEDS AN EXCHANGE ARGUMENT
Status: one fully reasoned greedy pattern, not a claim that greedy solves all
scheduling. Complete program interval_schedule.cpp.

[Rehearsal requests A[0,6),B[1,3),C[3,5),D[5,7). One room,
maximize count of complete requests; no extra setup time or values.]
Rohail has one rehearsal room and several requested time
intervals. He wants to accept as many complete requests
as possible without overlap. All requests count equally, and
there is no extra setup time between them in this
model. Intervals are half-open, so one request may
start exactly when the previous one ends. Those assumptions
define the objective. If some performances were more valuable
or required travel time, the same choice rule would
need a new proof or a different algorithm.

[Earliest-start chooses longA and blocksB,C,D. Earliest-finish choosesB,C,D.]
Rohail gives the room to the first request on the clock. Maya lays
the remaining requests beneath it, and they see who gets locked out. The long request from zero to six
starts first, but choosing it blocks the three requests
one to three, three to five and five to
seven. We could accept three instead of one. A
more promising rule is to choose the request that ends
earliest, leaving as much time as possible for later
requests. That intuition suggests a method, but it does
not finish the proof. We still need to show
that committing to the earliest finish cannot destroy an
optimal solution.

[Sort by end: B3,C5,A6,D7. SelectB;selectC;rejectA;selectD.]
Sort requests by their end times. Scan in that
order, accepting a request whenever its start is at
least the end of the last accepted request. In
our example, accept one to three, then three
to five. Reject zero to six because it overlaps
the accepted schedule. Accept five to seven. The
result contains three requests. Equal end times can be
handled with a consistent tie order; any compatible earliest
finishing choice supports the same basic argument for this
unweighted problem.

[Exchange picture: optimal first intervalO ends no earlier than greedyG.
ReplaceO withG; all later optimal starts remain legal.]
Take any optimal schedule and look at its first
interval. The greedy interval ends no later than that
one, because it has the earliest available finish.
Replace the optimal schedule's first interval with the greedy
choice. Every later interval still starts late enough,
so the replacement preserves feasibility and the number of
accepted requests. Therefore there exists an optimal schedule
beginning with the greedy choice. Apply the same reasoning
to the remaining compatible intervals, and repeat. This
exchange argument turns the local choice into a global
correctness proof.

[Wrong alternative: shortest duration selects[3,5) but blocks[0,4),[4,8).]
Sam suggests the shortest request instead. Rohail wants a counterexample
before replacing one unproved rule with another.
Consider intervals zero to four, four to eight,
and three to five. The shortest interval, three
to five, overlaps both longer ones. Choosing the
two touching longer intervals gives a count of two,
while choosing the middle one leaves only one. Duration
alone ignores where a request lies. A counterexample is
valuable because it tells us exactly which intuitive rule
fails, instead of making us distrust every greedy method
that ever feels plausible.

[Code stores(end,start,originalID); accepted end updates only on selection.]
The complete program stores end time first so ordinary
tuple sorting gives the desired order, retaining start time
and original request ID. It updates the previous end
only when it accepts a request. Updating it for
a rejected interval would change the meaning of the
state and could wrongly block later requests. The invariant
is that the chosen list is a feasible earliest-finish
greedy schedule among the intervals examined so far, with
previous end describing its last accepted interval. An empty
input gives an empty schedule, not a fabricated first
request.

[Complexity and limitation: weighted value objective can favor one long interval.]
Sorting costs order n log n, and the scan
costs order n. We store the requests and the
chosen IDs in linear space. If requests have different
values and the objective is maximum total value, accepting
the most requests is no longer the same objective.
A valuable long interval might beat several cheap short
ones. Weighted interval scheduling is a dynamic-programming extension,
not something this count-maximizing proof already solves. Keep the
word best attached to an explicit quantity.

Earliest finish selects the first
request, skips the overlapping middle request, and accepts
two to four, giving two. The shared endpoint
is allowed because of our half-open convention. If a
different problem requires a gap between rehearsals, change the
compatibility test and prove the changed model. Our small-case
oracle enumerates all request subsets, checks overlap directly,
and compares the maximum count with the program's result.
It also checks that every returned original ID belongs
to a distinct, compatible request.
