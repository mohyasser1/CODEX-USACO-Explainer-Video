PART 2 GUIDED LAB — ONE DASHBOARD, TWO DIFFERENT PREFIX PASSES
Status: substantive integration lab. Program batch_dashboard.cpp.

[Initial counts2,1,3,0,4. Updates all precede queries. Add2 on[1,4);add-1 on[2,5).]
Rohail has learned several fast techniques, but Maya gives him a problem without naming any of them. Their attendance dashboard contains five counts: two, one, three, zero and four. Before the dashboard opens, two corrections arrive. Add two to positions one through four, excluding four. Then subtract one from positions two through five, excluding five. After all corrections are finished, the dashboard must answer many interval-sum questions. The order of these phases is part of the contract: every correction comes first, every query afterward. We are not being asked to answer a query halfway through the updates.

[Three stages on board: record corrections; build final values; answer static sums.]
Rohail reaches for the newest data structure he has heard about. Maya asks him to write the timeline before choosing a tool. The corrections can be collected as boundary events because nobody needs intermediate values. Once the final sequence is known, it stays fixed during the query phase, so ordinary prefix sums are enough. Their plan has three stages: record changes, reconstruct the corrected values, and build a query table. The interesting work is choosing compatible representations and connecting them correctly. Knowing the name of a more advanced tree does not make that tree necessary for this workload.

[Difference events length6: update[1,4)+2 means diff1+2,diff4-2.]
Start with a difference-event array of six zeros. Five values need six boundaries, including the boundary just after the final element. The first correction adds two at boundary one and subtracts two at boundary four. While reconstructing from left to right, the active correction will begin at one and stop before four. Notice that we are recording corrections, not converting the original values into their difference array. The original sequence remains stored separately. This choice simplifies the explanation: the running sum of events tells us what to add to each original value, rather than pretending the events already contain the original counts.

[Second update[2,5)-1: diff2-1,diff5+1. Events0,2,-1,0,-2,1.]
The second correction has delta negative one. Add negative one at boundary two, and subtract negative one at boundary five. Subtracting negative one means adding one. Rohail initially writes negative one at both ends, which would keep decreasing the active correction instead of stopping it. Maya asks what the two events must sum to for an update that eventually ends. They must cancel. The correct event array is zero, two, negative one, zero, negative two and one. The last event is a stop signal at boundary five, not a sixth attendance count.

[Reconstruction table index0..4;active0,2,1,1,-1;final2,3,4,1,3.]
Now reconstruct carefully. At index zero, the active correction is zero, so the original two stays two. At index one, the event adds two to active, giving two; original one becomes three. At index two, the negative-one event reduces active to one; original three becomes four. Index three has no event, so active remains one and original zero becomes one. At index four, the negative-two stop reduces active to negative one; original four becomes three. The final values are two, three, four, one and three. Each value combines original data with active corrections; neither component alone is the final answer.

[Sanity check: original sum10; first update adds6; second subtracts3; final13.]
Maya checks the whole-array total without using the reconstruction table. The original values sum to ten. The first update affects three positions and adds two to each, increasing the total by six. The second affects three positions and subtracts one from each, decreasing the total by three. The new total should therefore be thirteen. Adding the five reconstructed values also gives thirteen. This does not prove every position is correct, but it is an independent arithmetic check that can catch a sign mistake or a wrong endpoint. Rohail keeps both the local trace and the global consistency check.

[Build prefix from final values:0,2,5,9,10,13. Different array, different meaning.]
Next build the query prefix table from the final values, starting with a leading zero. After the first value the prefix is two. Then it becomes five, nine, ten and thirteen. The completed table is zero, two, five, nine, ten, thirteen. We have used a running sum twice, but the two passes mean different things. Summing difference events reconstructs how much each position changes. Summing corrected values records how much the first several positions contain. Maya asks Rohail to label both arrays before they write code. Similar loops do not give their variables interchangeable meanings.

[Queries[1,4)=10-2=8;[0,5)=13;[3,3)=0.]
For the query from one through four, excluding four, subtract prefix one from prefix four: ten minus two gives eight. The selected final values are three, four and one, which also sum to eight. The whole-array query is prefix five minus prefix zero, giving thirteen. An empty query from three to three subtracts a prefix from itself and returns zero. No special branch is needed for that case. These formulas use half-open boundaries consistently. If an external statement uses inclusive endpoints, perform the conversion at the input boundary rather than mixing two coordinate conventions inside the same proof.

[Code input n,u,q; n values; u updates(l,r,delta); q queries(l,r).]
Our standalone program reads the number of values, updates and queries first. It then reads the original values, all updates, and finally all queries. This layout enforces the offline timeline we designed. Each update validates that its left boundary is no greater than its right boundary and both lie between zero and n. It writes two events. The reconstruction loop accumulates active, adds it to the original value, and extends the query prefix in the same pass. Combining those last two operations is safe because the prefix uses the corrected current value after its update, not the old value before the correction.

[Proof invariant:active=sum of deltas with l<=i<r;prefix[i]=sum final values beforei.]
The combined pass has two useful invariants. After applying the event at index i, active equals the sum of all correction deltas whose intervals contain i. This follows because each update contributes from its start until its stop cancels it. Before extending the query prefix, prefix i equals the sum of final values strictly before i. Adding the corrected value at i produces prefix i plus one with the required meaning. The two facts connect: the first proves that the value we add is correct, and the second proves that the table stores the correct accumulated sum. This is a small pipeline proof, not an appeal to two memorized tricks.

[Counterexample unsafe bound: n=u=100000,delta10^9 ->sum10^19.
Actual contract n,q<=100000;u<=10000;|a|<=10^9;|delta|<=10^6.
Absolute total<=100000*(10^9+10000*10^6)=1.1*10^15.]
Now check the numeric bounds before congratulating the algorithm. Suppose there were one hundred thousand positions, one hundred thousand updates, and each update added a billion across the entire array. The final sum would be around ten to the nineteenth, beyond signed sixty-four-bit range. Long long is larger than int, but it is not unlimited. Our teaching contract therefore limits the total number of updates to ten thousand and each update magnitude to one million, while original values may have magnitude up to one billion. The absolute whole-array total is then at most about one point one times ten to the fifteenth, comfortably inside long long. The bounds must match the code.

[Complexity O(n+u+q),storageO(n); online queries would change workload.]
Each correction writes two events, reconstruction scans n positions, and each query uses two prefix entries. Total time is order n plus u plus q, with linear storage. If Maya now asks for answers after every update, this program's timing no longer matches the request. Reconstructing everything each time can be expensive; that is when a suitable dynamic structure becomes relevant. Rohail writes the phase assumption above the routine. A method can be efficient and correct for its stated workload while being unsuitable for a changed one. The goal is to recognize the change instead of silently returning stale prefix answers.

[Transfer question: initial1,0,2;add3 on[0,2);add-2 on[1,3);query[0,3),[1,2).]
Try a fresh dashboard with values one, zero and two. Add three to the half-open interval zero through two, then subtract two on one through three. Find the event array, final values and prefix table. Answer the whole-array query and the one-element query from one through two. Also explain what a correction on the empty interval two through two should do. Pause the video before continuing. Keep the arrays on separate lines so you can see which quantities are corrections and which are final counts; merging their labels would make a correct number surprisingly hard to interpret.

[Answer events3,-2,-3,2;active3,1,-2;final4,1,0;prefix0,4,5,5;queries5,1.]
The events are three, negative two, negative three and two. Their running corrections are three, one and negative two. Adding those to the original values gives four, one and zero. The prefix table is zero, four, five, five, so the queries return five and one. An empty update writes opposite events at the same boundary, which cancel. Our independent test oracle applies every update directly to each covered element, then scans each requested interval. It deliberately does the slower obvious work rather than sharing the optimized event logic. When the two disagree, save that small input and inspect the first state where their meanings diverge.
